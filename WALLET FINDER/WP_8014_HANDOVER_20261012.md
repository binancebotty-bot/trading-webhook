## 1. The defect (confirmed, source-proven)

`HL_Copy_Engine_SSOT.py` **L1991–1992**:

```python
oid = str(raw_get(raw, "oid", "hash", "tid", "id", default=""))
fill_id = str(raw_get(raw, "fill_id", default="")) or \
          f"{wallet}:{coin}:{ts}:{side}:{size:.12g}:{price:.12g}:{oid}"
```

The internal `fill_id` uses the ORDER id (`oid`) and **never the native trade id (`tid`)**. Several
genuinely-distinct fills of one order with the same ts/size/price/side therefore collapse under dedup.

**Proven impact:** order `oid=570624315083` on `xyz:UNITREE` — 39 exchange fills (39 distinct tids)
produce 32 internal ids; **7 executions are lost** (six 1.0-fills collapse to one; a 1.54 pair collapses
to one). That 7 × net **−7.54** is the entire `XYZ:UNITREE` reconciliation gap
(engine internal −165.95 vs exchange-implied −173.49).

## 3. What Hermes did NOT prove (the gaps the controller flagged — MUST be completed)

1. **Backward-compatible deduplication is NOT in the reviewable patch.** The patch shows only the id
   change. A naive deploy re-ingesting the affected window WOULD double-count the existing 75 rows,
   because their persisted ids use the legacy composite while new rows use `…:oid:tid`. The required
   behaviour is a **multiset-aware ingest**: for each legacy composite, count how many rows the ledger
   already holds and accept only the difference the exchange reveals. (Hermes demonstrated this in a
   standalone replay — `probes/isolated_engine_tid_fix_readonly.py`: 75 existing + exactly 7 accepted,
   second pass 0 — but it is **not wired into the engine's real ingestion path**.)
2. **The engine's REAL ingestion path was not exercised end-to-end** — `ingest_fetched_rows()` /
   `accept_fill()` / `_remember_id()` (the `seen_set` dedup) were not driven.
3. **Ledger persistence + genuine restart/rebuild were not exercised** through the engine's own
   mechanisms (`rebuild_from_ledger()`, the append-only `raw_live_fills.csv`, `_seen_fill_ids`).
